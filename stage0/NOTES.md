## 0-1. 역사 (2026-10-13)

### 핵심

- MuJoCo = Multi-Joint dynamics with Contact. 워싱턴 대학교의 에마누엘 토도로프가 만들었고, 2012년 논문 "MuJoCo: A physics engine for model-based control"로 처음 소개했다.
- 출발점은 게임이 아니라 모델 기반 제어다. 시뮬레이터로 수없이 미리 돌려 보고 가장 좋은 동작을 고르는 방식이라 엔진에 세 가지가 필요했다.

  - 거꾸로(역동역학)도 계산할 것: 물체끼리 닿아 있을 때도
- 연표: 2012 논문 → 2015~ Roboti 유료 판매 → 2016 OpenAI Gym으로 강화학습 표준 시험 환경이 됨 → 2018 DeepMind Control Suite → 2021.10 Google DeepMind 인수·무료화(2.1.0) → 2022.3 공식 Python 바인딩(2.1.2) → 2022.5 오픈 소스(2.2.0, Apache 2.0) → 2023.10 3.0·MJX → 2025.3 Newton 발표(MuJoCo Warp 포함) → 2026.2 MuJoCo Warp 정식 출시(3.5.0) → 2026.10 3.15.0

- MuJoCo는 Multi-Joint dynamics with Contact의 줄임말이다. 여러 관절로 이어진 물체들이 서로 닿으면서 움직이는 것을 계산하는 엔진이라는 뜻이다.

- 워싱턴 대학교의 에마누엘 토도로프가 만들었고, 2012년 논문 "MuJoCo: A physics engine for model-based control"(모델 기반 제어를 위한 물리 엔진)으로 처음 소개했다.

  (3) 거꾸로도 계산할 수 있어야 한다: "이렇게 움직이려면 힘이 얼마나 필요한가"(역동역학)를 계산할 수 있고, 물체끼리 닿아 있을 때도 계산된다.
- 화면에서 자연스럽게 보이는 것이 더 중요한 게임용 물리 엔진과는 출발점이 다르다.

- 2018: DeepMind Control Suite도 MuJoCo로 만들어짐
- 2021년 10월: Google DeepMind가 인수하고 무료로 공개 (버전 2.1.0)
- 2022년 3월: 공식 Python 바인딩 (2.1.2, pip install mujoco)
- 2022년 5월: 소스 코드 전체 공개, 오픈 소스가 됨 (2.2.0, Apache 2.0 라이선스)
- 2023년 10월: MuJoCo 3.0. GPU·TPU에서 대량 병렬로 돌리는 MJX 추가

## 0-2. 무엇을 해 주나 (회사 PC에서 진행, 2026-10-14 기록)

회사 PC에서 진행했지만 기록이 남지 않아서, 집 PC에서 꼭지 범위에 맞춰 핵심을 다시 정리했다. 그때 나온 질문이나 헷갈린 점은 기록에 없다.

### 핵심

- 넣는 것은 세 가지다.
  - 모델: 몸체, 관절, 모양, 질량, 모터를 적은 설계도. MJCF나 URDF로 적고 컴파일하면 `MjModel`이 된다. 시뮬레이션하는 동안 바뀌지 않는다.
  - 상태: 지금 관절 위치(`qpos`)와 속도(`qvel`).
  - 제어 입력(`ctrl`): 모터에 주는 명령.
- 나오는 것은 아주 짧은 시간(기본 0.002초) 뒤의 상태와, 그 과정에서 계산한 값들이다: 각 부품의 위치·방향, 닿은 곳과 접촉력, 가속도, 센서 값. 이렇게 매 순간 바뀌는 값은 모두 `MjData`에 담긴다.
- 기본 원리: 시간을 잘게 쪼개 한 칸씩 앞으로 간다. 영화 필름이 한 장씩 이어져 움직임이 되는 것과 같다. 한 칸(`mj_step` 한 번)에서 하는 일은 다음과 같다.
  1. 지금 관절 각도로 각 부품이 어디에 있는지 계산한다(순기구학).
  2. 서로 닿은 곳을 찾는다(충돌 검사).
  3. 힘을 모은다: 중력, 모터, 스프링 같은 힘.
  4. 닿은 곳에서 서로 파고들지 않게 밀어내는 힘(접촉력)을 함께 풀고, 전체 힘으로 가속도를 구한다(F = ma).
  5. 가속도로 속도와 위치를 조금 바꾼다(적분). 이것이 다음 칸의 상태다.
- 공식 문서는 `mj_step`이 "연속 시간에서 순동역학을 계산한 다음, `timestep`만큼 적분한다"고 설명한다. 문서는 4번의 접촉력 계산을 "어려운 부분"이라고 부르며, MuJoCo의 개성이 가장 많이 드러나는 곳이다(5단계에서 본다).
- 1번과 2번은 `mj_kinematics`, `mj_collision`처럼 따로 부를 수도 있다. 시간을 앞으로 보내지 않고 자세나 충돌만 알고 싶을 때 쓴다. 3~5번(시간을 앞으로 보내는 부분)은 1단계 실험에서 직접 본다.

### 메모

- 회사 PC 세션의 질문, 헷갈린 점, 예측 질문은 기록되지 않았다.
- 기록은 "다음"이라고 할 때 남기므로, "다음" 없이 세션이 끝나면 기록이 빠진다. 이번이 그 경우다.

### 출처

- [MuJoCo 공식 문서: Simulation](https://mujoco.readthedocs.io/en/stable/programming/simulation.html) — `mj_step`이 하는 일, `mjModel`(모델 설명)과 `mjData`(계산 작업 공간)
- [MuJoCo 공식 문서: Computation](https://mujoco.readthedocs.io/en/stable/computation/index.html) — 순기구학 → 힘 → 제약력(접촉력) → 가속도 → 적분
- 기본 시간 간격 0.002초: mujoco 3.15.0에서 빈 모델의 `opt.timestep`을 출력해 확인했다.

## 0-3. 어디에 쓰이나 (2026-10-14)

### 핵심

- 쓰임새는 크게 세 가지다. 셋 다 "현실에서 하기 전에 가상 세계에서 먼저 해 본다"는 점은 같고, 언제·얼마나 많이·얼마나 정확히 돌리느냐가 다르다.

| 쓰임새 | 언제 돌리나 | 얼마나 돌리나 | 특히 중요한 것(0-1의 세 가지 요구 중) |
|---|---|---|---|
| 연습장(강화학습) | 로봇을 쓰기 전에 미리 | 아주 많이(예: 100년 치 경험) | 빠를 것 |
| 수읽기(예측 제어) | 로봇이 움직이는 도중에 계속 | 짧은 미래를 여러 번, 실제 시간보다 빨리 | 빠를 것 + 정확할 것 |
| 시험대(검증·연구) | 만들기 전, 실제로 돌리기 전 | 확인할 장면만 | 정확할 것 + 거꾸로 계산 |

- 연습장: 시뮬레이터에서 시행착오로 배우고 결과만 실제 로봇에 옮긴다(sim-to-real).
  - OpenAI 로봇 손(2018): 블록 돌리기를 MuJoCo 안에서만 배워 실제 Shadow Dexterous Hand로 옮겼다. 물리 값을 그대로 두면 약 3년 치(실제 1.5시간), 마찰 같은 값을 일부러 바꿔 가며 배우면 약 100년 치(실제 50시간) 경험이 들었다. 16코어 컴퓨터 384대로 1시간에 약 2년 치를 만들었다.
  - DeepMind 축구 로봇(2023): 관절 20개짜리 Robotis OP3가 1대1 축구를 MuJoCo에서만 배우고, 추가 학습 없이 실제 로봇에서 했다.
  - MuJoCo Playground(2025): MJX 기반. GPU 한 장으로 몇 분 만에 학습해 여러 로봇에 옮긴다.
- 수읽기: 매 순간 짧은 미래를 여러 번 굴려 보고, 가장 좋은 계획의 첫 동작만 실행한 뒤 다시 반복한다. MuJoCo가 처음부터 노린 "모델 기반 제어"가 이것이다. 예: MuJoCo MPC(MJPC, 2022).
- 시험대: Unitree의 공식 MuJoCo 시뮬레이터(unitree_mujoco)로 제어 프로그램을 먼저 시험한다. 역동역학으로 동작에 필요한 관절 힘을 계산해 모터를 고른다. 과학 연구에도 쓴다(가상 쥐, Nature 2024).

- 예 2: DeepMind의 축구 로봇 연구(2023년 공개, Science Robotics 게재). 관절 20개짜리 작은 인간형 로봇(Robotis OP3)이 1대1 축구를 MuJoCo 시뮬레이션 안에서만 배운 뒤, 추가 학습 없이 실제 로봇에서 그대로 축구를 했다.
- 요즘은 GPU로 여러 시뮬레이션을 한꺼번에 돌린다(MJX, MuJoCo Warp). MuJoCo Playground(2025)는 GPU 한 장으로 몇 분 만에 학습해서 그 결과를 네발 로봇, 인간형 로봇, 로봇 손, 로봇 팔에 옮길 수 있다고 소개한다.

3. 수읽기: 예측 제어(MPC)
- 체스 고수의 수읽기와 같다. 로봇이 움직이는 도중에 아주 짧은 간격마다 다음을 반복한다.
  (1) 지금 상태에서 "이렇게 움직이면 어떻게 될까"를 여러 가지로 짧게 시뮬레이션해 본다.
  (2) 가장 좋은 계획의 첫 동작만 실행한다.
  (3) 바뀐 상태에서 처음부터 다시 수읽기를 한다.
- MuJoCo가 처음부터 노린 쓰임새(모델 기반 제어)가 바로 이것이다.
- 그래서 필요한 것: 실제 시간보다 훨씬 빠를 것, 지금 상태에서 바로 시뮬레이션을 시작할 수 있을 것, 예측이 정확할 것.
- 예: Google DeepMind의 MuJoCo MPC(MJPC, 2022). MuJoCo로 실시간 예측 제어를 하는 오픈 소스 도구다. 네발 로봇, 두 팔로 물건 다루기, 루빅스 큐브 풀기, 인간형 로봇이 사람 동작 따라 하기 같은 예제가 있다.
- 강화학습과의 차이: 강화학습은 미리 연습해서 반사 신경을 만들어 두고, 예측 제어는 매 순간 생각해서 고른다.

4. 시험대: 검증과 연구
- 실제 로봇에 올리기 전에: 로봇 회사 Unitree는 자사 로봇(Go2, G1, H1 등)용 MuJoCo 시뮬레이터를 공식으로 내놓았다. 실제 로봇용 개발 도구로 짠 제어 프로그램을 시뮬레이터에서 먼저 돌려 보고 실제 로봇으로 넘어가게 하려는 것이다.
- 만들기 전에: 역동역학(거꾸로 계산)으로 "이 동작을 하려면 관절마다 힘이 얼마나 필요한가"를 계산할 수 있다. 어떤 모터를 고를지 정하는 근거가 된다.
- 과학 연구: 하버드 대학교와 Google DeepMind 연구진이 MuJoCo 안에 실제 쥐를 닮은 몸을 만들고, 인공 신경망이 그 몸을 움직이게 했다. 그 신경망의 활동은 같은 동작을 하는 실제 쥐의 뇌 활동을 잘 예측했다(Nature, 2024).

5. 핵심
- MuJoCo는 연습장(강화학습), 수읽기(예측 제어), 시험대(검증·연구)로 쓰인다.

- 그래서 MuJoCo에는 빠를 것, 정확하고 안정적일 것, 거꾸로도 계산할 것이 모두 필요했다.

## 0-4. 설계 철학 (2026-10-14)

### 핵심

- 우선한 것은 0-1의 세 가지 요구(빠를 것, 정확하고 안정적일 것, 거꾸로도 계산할 것)다.
- 기존 엔진은 두 진영이었다. 로봇·생체역학 엔진은 관절 좌표로 정확하지만 접촉에 약했다(스프링 방식은 아주 작은 시간 간격이 필요하다). 게임 엔진은 최적화로 접촉을 풀지만, 부품마다 따로 적고 관절을 조건으로 붙잡아서 복잡한 기구에서 부정확하고 불안정하다. MuJoCo는 관절 좌표와 최적화 접촉을 처음으로 합쳤다.
- 선택 1, 관절 좌표: 관절 6개짜리 팔을 부품마다 적으면 값 36개와 조건 30개, 관절 좌표로 적으면 값 6개다. 관절이 벌어지지 않는다. 대가: 기구의 고리는 허용되지 않아서 equality constraint로 따로 건다. 이 조건도 부드럽게 풀리므로 살짝 어긋날 수 있다.
- 선택 2, 부드럽고 볼록한 접촉: 딱딱한 접촉(LCP/NCP)은 NP-hard다. 제약을 조금 어겨도 되게 하는 대신 엄밀히 볼록한 문제로 바꿔서 답이 하나로 정해지고, 접촉 중에도 역동역학이 된다. 대가: 살짝 파고들고, 접촉 설정값에 따라 결과가 달라진다.
- 선택 3, 컴파일·미리 할당·모델과 데이터 분리: MJCF를 컴파일해 `MjModel`(바뀌지 않음)을 만들고, 상태와 중간 결과는 `MjData`에 둔다. 계산은 미리 잡아 둔 메모리 안에서만 한다. `MjData`를 여러 개 만들어 동시에 계산할 수 있다. 단계 함수와 플래그(중력·접촉 끄기 등)로 계산을 골라 쓸 수 있다.
- 덧붙여: 물리는 연속 시간(힘과 가속도)으로 정의되고, 적분기는 그 위에 따로 얹는다.

0. 한 줄 요약
- MuJoCo는 제어 연구에 쓰려고 "빠를 것, 정확하고 안정적일 것, 거꾸로도 계산할 것"을 우선했다. 그래서 (1) 관절 좌표로 계산하고, (2) 접촉을 부드럽고 볼록한 문제로 풀고, (3) 미리 컴파일한 설계도와 미리 잡아 둔 메모리 위에서 계산한다. 그 대가로 물체가 아주 살짝 파고드는 것 같은 근사를 받아들였다.

1. 지금까지 배운 것과 이번 주제의 위치
- 역사: MuJoCo를 처음 소개한 2012년 논문의 제목은 "MuJoCo: A physics engine for model-based control"(모델 기반 제어를 위한 물리 엔진)이다. 모델 기반 제어는 로봇이 시뮬레이터로 "이렇게 움직이면 어떻게 될까"를 수없이 미리 굴려 보고 가장 좋은 동작을 고르는 방식이다.
- 무엇을 해 주나: 설계도(모델), 지금 상태, 모터 명령을 넣으면 아주 짧은 시간 뒤의 상태가 나온다. 한 칸 계산은 "부품 위치 계산 → 닿은 곳 찾기 → 힘 모으기 → 접촉력과 가속도 구하기 → 속도와 위치 갱신" 순서다.
- 어디에 쓰이나: 연습장(강화학습), 수읽기(예측 제어), 시험대(검증·연구).
- 이번 주제는 "MuJoCo는 왜 이렇게 생겼나"다. 모든 것을 다 잘하는 엔진은 없다. 무엇을 우선하면 다른 무엇을 포기하게 된다. 설계 철학을 알면 MuJoCo가 어떤 상황에서 어떻게 행동할지 미리 짐작할 수 있고, 이상한 결과가 나왔을 때 그것이 버그인지 설계의 결과인지 가늠할 수 있다.

2. 무엇을 우선시했나: 세 가지 요구
- 빠를 것: 예측 제어는 로봇이 움직이는 동안 실제 시간보다 빨리 미래를 여러 번 굴려 봐야 한다. 강화학습은 엄청난 양의 연습 경험이 필요하다. 2012년 논문 기준으로 MuJoCo는 사람 모양 모델을 12코어 컴퓨터에서 1초에 약 40만 번 계산했다.
- 정확하고 안정적일 것: 예측이 틀리면 그 예측으로 고른 동작도 틀린다. 계산이 불안정해서 값이 튀면 예측 자체를 믿을 수 없다.
- 거꾸로도 계산할 것: 보통의 계산(순동역학)은 "이 힘을 주면 어떻게 움직이나"를 구한다. 거꾸로 계산(역동역학)은 "이렇게 움직이려면 힘이 얼마나 필요한가"를 구한다. 제어(필요한 모터 힘 계산)와 데이터 분석(움직임을 보고 그때 작용한 힘을 알아내기)에 쓰인다. MuJoCo는 물체끼리 닿아 있을 때도 이 계산이 되기를 원했다.

3. 기존 물리 엔진의 두 진영
(1) 로봇·생체역학 엔진
- 자세를 관절 좌표로 적는다. 관절 좌표란 "어깨 30도, 팔꿈치 45도"처럼 관절 값만으로 자세를 적는 방식이다.
- 로봇은 몸통에서 팔로, 팔에서 손으로 갈라지는 나무 구조다. 이 구조를 따라 차례로 훑는 효율적인 계산법(재귀 알고리즘)을 써서 정확하고 효율적이다.
- 약점: 접촉을 아예 빼거나, 접촉을 "아주 단단한 스프링"으로 흉내 냈다. 단단한 스프링은 아주 짧은 순간에 힘이 크게 바뀐다. 그래서 시간 간격을 아주 잘게 쪼개야 하고, 간격이 크면 그 변화를 놓쳐 계산이 튀어 버린다.
(2) 게임 엔진
- 접촉력을 "최적화 문제"를 풀어서 구하는 현대적인 방식을 쓴다. 최적화 문제란 여러 조건을 만족하는 답 가운데 가장 좋은 답을 찾는 문제다.
- 약점: 부품마다 위치와 방향을 따로 적고(부품 하나당 값 6개: 위치 3, 회전 3), 관절은 "이 두 부품이 여기서 떨어지면 안 된다"는 조건을 숫자로 맞춰서 붙잡는다. 값이 필요 이상으로 많고, 조건을 숫자로 맞추는 과정에서 오차가 생긴다. 그래서 관절이 많은 복잡한 기구에서는 부정확하고 불안정해진다.
- 게임은 화면에서 자연스럽게 보이는 것이 더 중요하다는 점에서 출발점이 다르다.
(3) MuJoCo
- 로봇 엔진의 장점(관절 좌표)과 게임 엔진의 장점(최적화로 접촉 풀기)을 합쳤다. 공식 문서는 MuJoCo가 이 조합을 개척했고, 이후 다른 시뮬레이터들이 이 방식을 받아들였다고 설명한다.

4. 선택 1: 관절 좌표로 계산한다(일반화 좌표)
- 관절 6개짜리 로봇 팔로 비교한다.
  - 부품마다 따로 적기: 부품 6개 × 값 6개 = 값 36개. 여기에 관절마다 "여기서 떨어지지 말고, 정해진 축으로만 돌아라"라는 조건이 5개씩 붙는다. 관절 6개면 조건 30개를 매 순간 맞춰야 한다. 36 − 30 = 6, 결국 실제로 자유롭게 움직일 수 있는 것은 6개뿐이다.
  - 관절 좌표로 적기: 관절 각도 6개. 처음부터 자유롭게 움직이는 6개만 적는다.
- 얻은 것
  - 관절이 벌어질 일이 애초에 없다. "떨어지지 마"가 적는 방식 자체에 들어 있어서 따로 지킬 필요가 없다. 그래서 정확하고 안정적이다.
  - 다룰 값이 적고, 나무 구조를 따라 효율적으로 계산할 수 있어서 빠르다.
- 대가
  - 기구가 나무처럼 갈라지기만 하는 모양이어야 한다. 공식 문서는 기구의 고리(kinematic loop)를 허용하지 않는다고 적고 있다. 평행 링크처럼 다시 이어지는 고리 모양 기구가 필요하면 "이 두 점을 붙여 둬라" 같은 조건(equality constraint)을 따로 건다.
  - 이 조건은 아래 선택 2의 접촉과 같은 방식(부드러운 제약)으로 풀린다. 그래서 고리를 닫는 이음매가 아주 살짝 어긋날 수 있다.
- 나중에 볼 것: 관절 좌표 방식 때문에 생기는 특징(예: 위치를 나타내는 값의 개수와 속도를 나타내는 값의 개수가 다를 수 있다)은 3단계(기구학)에서 다룬다.

5. 선택 2: 접촉을 부드럽고 볼록한 문제로 푼다
(1) 접촉 문제란
- 두 물체가 닿으면, 서로 파고들지 않게 밀어내는 힘과, 마찰 한도 안에서 미끄러짐을 막는 힘을 구해야 한다.
- 닿은 곳이 여러 군데면 각 접촉의 힘이 서로 영향을 주기 때문에 한꺼번에 풀어야 한다.
(2) 딱딱한 접촉(기존 방식)
- "파고듦은 정확히 0", "닿아 있을 때만 밀고, 떨어지는 중이면 힘은 0" 같은 규칙을 칼같이 지키려 한다.
- 이런 문제(LCP, NCP라고 부르는 형태)는 수학적으로 풀기 아주 어려운 부류(NP-hard)에 속한다.
- 완전히 딱딱하다고 가정하면 답이 하나로 정해지지 않는 경우도 있다. 예를 들어 다리 네 개짜리 탁자를 딱딱한 바닥에 놓으면, 네 다리가 받는 힘의 합은 정해지지만 그 힘을 네 다리가 어떻게 나눠 받는지는 하나로 정해지지 않는다.
(3) MuJoCo의 방식
- 규칙을 아주 조금 어기는 것을 허용한다(부드러운 접촉). 물체가 아주 살짝 겹칠 수 있고, 서로 멀어지는 중인데도 밀어내는 힘이 조금 남아 있을 수 있다.
- 대신 "규칙을 얼마나 어겼는지"에 벌점을 매기는 문제로 바꾼다. 이 문제는 그릇 모양(볼록, convex)이다. 공식 문서 표현으로는 "엄밀히 볼록(strictly convex)"하다.
- 근거: 실제 물체도 모두 조금씩은 변형된다(공식 문서). 그래서 부드러운 접촉이 오히려 현실에 가깝다고 본다. 탁자 예에서도 다리가 살짝 눌린다고 보면, 각 다리가 얼마나 눌렸는지에 따라 힘의 나눔이 하나로 정해진다.
(4) 볼록이 왜 좋은가
  볼록(그릇):          \_____/       구슬을 어디에 놓든 바닥 한 곳으로 굴러간다 → 답이 하나
  볼록 아님(골짜기들): \_/\__/\_/    출발점에 따라 다른 골짜기에서 멈춘다
- 답이 하나로 정해지고, 빠르고 안정적으로 찾을 수 있다.
(5) 거꾸로 계산이 된다
- 접촉력이 하나로 정해지기 때문에 "이 움직임을 만들려면 힘이 얼마나 필요한가"의 답도 하나로 정해진다. 공식 문서는 이 덕분에 접촉이 있어도 역동역학을 쉽게 계산할 수 있고, 제어와 데이터 분석에 유리하다고 설명한다.
- 2번에서 본 세 번째 요구(거꾸로 계산)를 이 선택이 해결했다.
(6) 대가
- 물체가 바닥에 가만히 놓여 있어도 아주 살짝 파고든다. MuJoCo에서 이것은 버그가 아니라 이 선택의 결과다.
- 접촉이 얼마나 단단하고 부드러운지 정하는 설정값이 있고, 그 값에 따라 파고드는 정도 같은 결과가 달라진다. 이 설정은 5단계(충돌과 접촉)에서 실험으로 다룬다.
(7) 참고
- MuJoCo의 제약 풀이는 접촉뿐 아니라 여러 종류의 마찰과 선택 1의 "붙여 두는 조건"까지 같은 틀에서 함께 다룬다.

6. 선택 3: 미리 컴파일하고, 메모리를 미리 잡아 두고, 설계도와 상태를 나눈다
(1) 컴파일
- 사람은 모델을 읽기 쉬운 XML 형식(MJCF)으로 적는다. 이름이 붙은 태그들이 겹겹이 들어 있는 형태다.
- 내장 컴파일러가 이것을 실행용 저수준 구조(MjModel)로 바꾼다. 공식 문서 표현으로 "서로 찾아갈 수 있게 엮이고(cross-indexed), 실행 계산에 최적화된" 형태다. 사람이 읽기 좋은 형태를 기계가 계산하기 좋은 형태로 미리 바꿔 두는 것이다.
(2) 메모리를 미리 잡아 두기
- 시뮬레이션 중의 계산은 XML을 읽고 컴파일할 때 미리 잡아 둔 메모리 안에서만 한다(공식 문서).
- 계산 도중에 메모리를 새로 마련하는 일은 느리고, 걸리는 시간도 들쭉날쭉하다. 미리 잡아 두면 빠르고, 매번 비슷한 시간에 계산이 끝난다. 실시간으로 미래를 굴려야 하는 예측 제어에서 중요하다.
(3) 설계도(MjModel)와 상태(MjData)를 나누기
- MjModel: 모델 설명. 시뮬레이션 중에 바뀌지 않는다고 전제한다.
- MjData: 매 순간 바뀌는 값(위치, 속도 등)과 계산 중간 결과 전부.
- 비유: 요리 레시피(MjModel) 한 장과 냄비(MjData) 여러 개. 같은 레시피로 냄비 여러 개를 동시에 끓일 수 있다.
- 설계도 하나로 MjData를 여러 개 만들면 여러 상태(여러 미래)를 동시에 계산할 수 있다. 모든 계산이 MjModel은 읽기만 하고 자기 MjData에만 쓰기 때문에, 여러 작업을 동시에 돌려도(멀티스레드) 안전하다(공식 문서).
- 이 구조는 예측 제어에서 여러 미래를 동시에 굴려 보는 일이나, 강화학습의 대량 시뮬레이션에 잘 맞는다.
- 앞에서 본 "넣는 것과 나오는 것"으로 보면, 설계도는 MjModel에, 지금 상태·모터 명령·계산 결과는 MjData에 들어 있다.
(4) 계산 단계를 골라 쓸 수 있다
- 시뮬레이션 한 칸(mj_step) 안의 단계들은 따로 부를 수도 있다. 예: 부품 위치만 계산하기(mj_kinematics), 닿은 곳만 찾기(mj_collision).
- 계산을 켜고 끄는 스위치(플래그)가 많다. 예를 들어 중력이나 접촉을 끈 채로 돌려 볼 수 있다. 결과가 이상할 때 원인을 좁히는 데 쓸 수 있다.
(5) 대가
- 설계도는 시뮬레이션 중에 바뀌지 않는다고 전제한다.

7. 덧붙여: 물리를 "연속 시간"으로 정의한다
- MuJoCo의 물리 모델은 "힘과 가속도"로, 끊김 없이 흐르는 시간 위에서 정의된다(공식 문서). 시간을 한 칸씩 앞으로 보내는 방법(적분기)은 그 위에 따로 얹는다.
- 그래서 한 칸 계산에서 "가속도 구하기"와 "속도·위치 갱신(적분)"이 별개 단계다. 공식 문서는 시뮬레이션 한 칸(mj_step)을 "연속 시간에서 순동역학을 계산한 다음, 정해진 시간 간격만큼 적분한다"고 설명한다.
- 적분 방법과 시간 간격은 6단계(구동과 적분)에서 다룬다.

8. 정리: 우선한 것 → 선택 → 얻은 것 → 대가
- 정확하고 안정적일 것 → 관절 좌표 → 관절이 벌어지지 않고, 값이 적어 빠르다 → 고리 모양 기구는 붙여 두는 조건으로 따로 걸어야 하고, 그 이음매는 살짝 어긋날 수 있다
- 거꾸로도 계산할 것 → 부드럽고 볼록한 접촉 → 답이 하나로 정해지고, 빠르고 안정적이며, 접촉 중에도 거꾸로 계산된다 → 아주 살짝 파고들고, 설정값에 따라 결과가 달라진다
- 빠를 것 → 미리 컴파일, 메모리 미리 잡기, 설계도와 상태 분리 → 빠르고 계산 시간이 일정하며, 여러 상태를 동시에 계산할 수 있다 → 설계도는 실행 중에 바뀌지 않는다고 전제한다
- 세 선택이 요구를 하나씩만 해결하는 것은 아니다. 예를 들어 관절 좌표와 볼록한 접촉도 속도에 도움이 된다. 위 연결은 "주로 어떤 요구에 답했나"를 기준으로 한 것이다.

9. 이걸 알면 미리 짐작할 수 있는 것
- 물체가 바닥에 아주 조금 묻혀 보인다 → 정상이다. 부드러운 접촉의 결과다.
- 고리 모양 기구의 이음매가 아주 살짝 벌어진다 → 붙여 두는 조건도 부드럽게 풀리기 때문이다.
- 같은 모델로 여러 시뮬레이션을 동시에 돌리고 싶다 → MjData를 여러 개 만든다.
- 접촉 설정값을 바꾸면 파고드는 정도가 달라진다 → 5단계에서 실험한다.

10. 핵심 세 줄
- MuJoCo는 로봇 엔진의 장점(관절 좌표)과 게임 엔진의 장점(최적화로 접촉 풀기)을 처음으로 합쳤다.
- 접촉은 아주 살짝 겹치는 것을 허용하는 대신 볼록한 문제로 바꿔서, 답이 하나로 정해지고 접촉 중에도 거꾸로 계산이 된다.
- 속도를 위해 미리 컴파일하고 메모리를 미리 잡아 두며, 바뀌지 않는 설계도(MjModel)와 바뀌는 상태(MjData)를 나눴다.
```

## 0-5. 전체 구조 (2026-10-14)

### 핵심

- 흐름: MJCF/URDF → (`mj_parseXML`) mjSpec → (`mj_compile`) mjModel → (`mj_makeData`) mjData → `mj_step` 반복(= `mj_forward` + 적분) → 그리기(mjv_가 mjvScene을 정리하고 mjr_(OpenGL)이나 mjrf_(Filament)가 그린다). `mj_loadXML`은 읽기와 컴파일을 한 번에 한다. `mj_recompile`을 쓰면 시뮬레이션 도중에도 모델을 고칠 수 있다.
- 본체는 C 라이브러리다(주 헤더 mujoco.h). 파이썬 바인딩은 pybind11로 만든 저수준 바인딩이다. `mujoco.viewer`는 simulate 앱과 같은 코드를 쓴다. MJX(JAX 구현·Warp 구현)는 별도 패키지이고, 모델 컴파일과 그리기는 본체에 맡긴다.
- `mj_step` 안(3.15.0 소스): `mj_checkPos`/`mj_checkVel` → `mj_forward`[`mj_fwdPosition`(기구학, 질량 행렬, 충돌, 제약 만들기) → 위치 센서 → `mj_fwdVelocity`(수동 힘, 바이어스 힘) → 속도 센서 → `mjcb_control` → `mj_fwdActuation` → `mj_fwdAcceleration` → 제약 단계 → 가속도 센서] → `mj_checkAcc` → 적분기. 검사 함수는 값이 망가지면 시뮬레이션을 자동으로 초기화한다.
- 단계가 위치 → 속도 → 구동 → 가속도 순서라서, `mj_forwardSkip`으로 바뀐 단계부터 다시 계산할 수 있다(격자 샘플에서 약 2배 빨라진다).
- 이름 규칙: mj_(시뮬레이션), mju_(유틸리티, mjModel·mjData를 받지 않음), mjv_(시각화), mjr_·mjrf_(렌더링), mjui_(UI), mjd_(미분), mjs_(모델 편집), mjcb_(콜백). 타입은 mj, mjt(기본 타입·열거형), mjf, mjs, mjv, mjr, mjrf, mjui. 열거형 값은 mjGEOM_BOX 꼴이다. 파이썬에서는 구조체만 첫 글자를 대문자로 바꾸고(MjModel), 함수는 이름이 같다.
- 변수 이름: n…(개수), q…(관절 좌표 공간), x…(세계 기준), 부품종류_속성(mjModel 배열), …id·…adr(다른 배열을 가리키는 번호), efc_…(제약). body 0번은 world다. mjData 변수는 위치 / 위치·속도 / 위치·속도·제어·가속도 의존으로 묶여 있다.

- 헤더 파일은 C에서 "이런 함수와 구조체가 있다"를 적어 둔 목록 파일이다. 주 헤더 파일 mujoco.h가 모든 API 함수를 정의하고 다른 헤더 파일들을 포함한다. mjModel은 mjmodel.h에, mjData는 mjdata.h에 정의되어 있다.
- 파이썬 mujoco 패키지: C 라이브러리를 파이썬에서 거의 그대로 부를 수 있게 만든 연결층(바인딩)이다. C++와 pybind11이라는 도구로 만들었고, 공식 문서는 MuJoCo 라이브러리에 최대한 직접 접근하도록 만든 저수준 바인딩이라고 설명한다.
- 뷰어: MuJoCo 배포판에는 simulate라는 앱이 들어 있고, 파이썬의 mujoco.viewer는 simulate와 같은 코드를 바탕으로 만들어졌다.
- GPU용 구현: MJX는 JAX(파이썬 계산 도구)에서 MuJoCo를 쓰게 해 주는 API이고, JAX로 짠 구현과 Warp로 짠 구현이 있다. MuJoCo Warp는 NVIDIA GPU에 맞춘 구현이다. MJX는 mujoco-mjx라는 별도 패키지이며, 모델 컴파일과 그리기는 본체인 mujoco 패키지에 맡긴다. 즉 MJX로 GPU에서 돌릴 때도 모델을 읽고 컴파일하는 일은 본체가 한다.

3. 지도 한 장: 모델이 시뮬레이션이 되기까지

  [사람이 쓰는 모델 파일]   MJCF(MuJoCo 고유의 XML 형식) 또는 URDF(로봇 분야에서 널리 쓰이는 XML 형식)
           │  읽기(파싱): mj_parseXML
           ▼
  [편집 가능한 모델 명세]   mjSpec      ← 코드로 직접 만들거나 고칠 수도 있다(mjs_ 함수)
           │  컴파일: mj_compile        (mj_loadXML은 읽기와 컴파일을 한 번에 한다)
           ▼
  [실행용 설계도]           mjModel     크기(n…), 옵션(opt), 부품별 배열(body_…, jnt_…, geom_…)
           │  mj_makeData
           ▼
  [상태와 계산 결과]        mjData      qpos, qvel, ctrl, xpos, contact, sensordata …
           │  mj_step을 반복 (= mj_forward + 적분)
           ▼
  [그리기]                  mjv_ 함수가 장면을 정리(mjvScene) → mjr_(OpenGL) 또는 mjrf_(Filament)가 실제로 그린다

(1) 모델 파일과 mjSpec
- mjSpec은 MJCF와 일대일로 대응하는 모델 명세다. MuJoCo의 XML 읽기 기능(MJCF, URDF 모두)도 모델을 불러올 때 이 mjSpec을 거친다.
- 파일 없이 코드로 모델을 조립할 수도 있다. 예를 들어 mjs_addGeom은 모양(geom)을 하나 추가하는 함수다.
- 파이썬에서는 mujoco.MjSpec 객체로 같은 일을 한다(MjSpec.from_file로 파일 읽기, compile로 컴파일).
(2) 컴파일과 mjModel
- 컴파일러는 mjSpec을 검사하고 실행용 설계도(mjModel)로 바꾼다. 틀린 값이 있으면 오류를 낸다. 예를 들어 크기가 0인 모양을 넣으면 "size 0 must be positive in geom"이라는 오류가 난다.
- 파이썬에서 XML로 바로 mjModel을 만들 때는 mujoco.MjModel.from_xml_path(파일) 또는 from_xml_string(문자열)을 쓴다.
- mjModel은 시뮬레이션 중에 바뀌지 않는다고 전제한다. 모델 구조를 바꾸고 싶으면 mjSpec을 고쳐 다시 컴파일한다. mj_recompile을 쓰면 시뮬레이션 상태를 유지한 채 mjModel과 mjData를 새 모델에 맞게 고쳐 주므로, 시뮬레이션 도중에도 모델을 편집할 수 있다(공식 문서).
(3) mjData
- C에서는 mj_makeData로, 파이썬에서는 mujoco.MjData(모델)로 만든다.
- 상태(qpos, qvel 등), 입력(ctrl 등), 계산 결과(xpos, contact, qacc, sensordata 등)가 모두 여기에 있다.
(4) 그리기
- mjv_ 함수들이 mjData를 보고 "무엇을 어디에 어떤 모양으로 그릴지"를 장면(mjvScene)으로 정리한다. 공식 문서 표현으로 mjvScene은 한 프레임의 3차원 장면과 장식을 완전하게 기하학적으로 설명한 것이다.
- mjr_ 함수들(OpenGL) 또는 mjrf_ 함수들(Filament)이 실제로 화면이나 이미지에 그린다.
- 나눈 이유(공식 문서): 장면 정리와 조작 로직을 그래픽 API(그림을 그리는 도구)와 독립시키고, 여러 그리기 방식이 같은 카메라, 선택, 물체를 마우스로 끌어당기기, 옵션 기능을 함께 쓰게 하려는 것이다.

4. mj_step 안쪽: 단계별 함수 (mujoco 3.15.0 소스 기준)

  mj_step
   ├─ mj_checkPos, mj_checkVel   위치·속도 값이 망가지지 않았는지 검사
   ├─ mj_forward                 순동역학: 지금 상태에서 가속도까지 계산한다(시간은 아직 안 간다)
   │   ├─ mj_fwdPosition         위치에만 기대는 계산: 부품 위치(기구학), 질량 행렬, 충돌 검사, 제약 만들기
   │   ├─ 위치 센서 계산
   │   ├─ mj_fwdVelocity         위치와 속도에 기대는 계산: 스프링·댐퍼 같은 수동 힘, 바이어스 힘
   │   ├─ 속도 센서 계산
   │   ├─ mjcb_control           사용자가 끼워 넣은 제어 함수(있으면 여기서 불린다)
   │   ├─ mj_fwdActuation        제어 입력(ctrl)을 모터 힘으로 바꾼다
   │   ├─ mj_fwdAcceleration     제약이 없다고 칠 때의 가속도를 구한다
   │   ├─ 제약 단계(mj_fwdConstraint)  접촉 같은 제약의 힘을 풀고 최종 가속도를 정한다
   │   └─ 가속도 센서 계산
   ├─ mj_checkAcc                가속도 값 검사
   └─ 적분기                      가속도로 속도와 위치를 한 칸 앞으로 보내고 시간을 늘린다

- 질량 행렬: 지금 자세에서 각 관절이 얼마나 무겁게 움직이는지를 담은 정보다(4단계에서 다룬다).
- 바이어스 힘: 중력, 그리고 몸이 회전하며 움직일 때 생기는 힘을 합친 것이다.
(1) 앞에서 본 다섯 단계와 짝짓기
- 부품 위치 계산 → mj_fwdPosition의 기구학
- 닿은 곳 찾기 → mj_fwdPosition의 충돌 검사(mj_collision)
- 힘 모으기 → mj_fwdVelocity(수동 힘, 바이어스 힘)와 mj_fwdActuation(모터 힘)
- 접촉력과 가속도 구하기 → mj_fwdAcceleration과 제약 단계
- 속도와 위치 갱신 → 적분기
(2) mj_forward와 mj_step의 차이
- mj_forward는 지금 상태에서 가속도(상태가 변하는 빠르기)까지만 계산하고 시간을 보내지 않는다.
- mj_step은 mj_forward를 한 다음 적분까지 해서 시간을 timestep만큼 앞으로 보낸다.
- 시간을 보내지 않고 지금 상태의 계산 결과(위치, 접촉 등)만 보고 싶으면 mj_forward를 쓴다.
(3) 거꾸로 계산: mj_inverse
- qpos, qvel, qacc(원하는 가속도)를 넣으면, 그 가속도를 만들려면 어떤 힘이 작용했어야 하는지(qfrc_inverse)를 계산한다. 공식 문서는 부드러운 제약 모델 덕분에 역동역학이 잘 정의되고 아주 효율적으로 계산된다고 설명한다.
(4) 왜 "위치 → 속도 → 구동 → 가속도" 순서인가
- 뒤 단계는 앞 단계 결과에 기대지만, 앞 단계는 뒤 단계 값에 기대지 않는다. 위치만 알면 할 수 있는 계산을 먼저 하고, 속도가 필요한 계산을 그다음에, 제어 입력이 필요한 계산을 그다음에 한다.
- 그래서 바뀐 것만 다시 계산할 수 있다. mj_forwardSkip은 앞 단계를 건너뛰는 버전이다. 공식 문서에 따르면, 여러 샘플이 중심점에서 위치만 또는 속도만 또는 제어만 다르게 격자 모양으로 놓여 있을 때 이 방식으로 성능이 약 2배 좋아진다. 조금씩 바꿔 보며 변화를 재는 미분 계산과 샘플링에 쓰인다.
- 제어 연구용으로 만든 설계가 여기에도 드러난다.
(5) 검사 함수
- 공식 문서: 검사 함수들은 숫자 값이 잘못되었거나 너무 커지면 시뮬레이션을 자동으로 초기화한다. 그래서 시뮬레이션이 갑자기 처음 상태로 돌아가면, 계산이 망가져서 검사 함수가 초기화했을 가능성을 의심해 볼 수 있다.
(6) 적분기 종류
- mujoco 3.15.0에는 Euler, RK4, implicit, implicitfast, discrete 다섯 가지 적분 방식이 있다. 어떤 것을 쓸지는 mjModel.opt.integrator에 적혀 있다. 자세한 것은 6단계(구동과 적분)에서 다룬다.

5. 이름 규칙 1: 함수와 타입의 앞머리 (공식 문서)
(1) 함수 앞머리
- mj_: 핵심 시뮬레이션 함수. 예: mj_step, mj_forward, mj_inverse, mj_kinematics, mj_collision
- mju_: 유틸리티 함수. 공식 문서 표현으로 mjModel과 mjData를 받지 않는 독립적인 함수다. 벡터를 0으로 채우는 mju_zero, 복사하는 mju_copy, 더하는 mju_addTo 같은 수학 계산 도구가 많다.
- mjv_: 추상 시각화 함수(무엇을 그릴지 장면 정리)
- mjr_: OpenGL 렌더링 함수, mjrf_: Filament 렌더링 함수(실제로 그리기)
- mjui_: UI(버튼, 패널 같은 화면 도구) 함수
- mjd_: 미분 계산 함수. 파이썬 mujoco 3.15.0에는 mjd_transitionFD, mjd_inverseFD, mjd_quatIntegrate, mjd_subQuat 네 개가 있다. 이름 끝의 FD는 조금씩 바꿔 보고 변화를 재서 미분을 숫자로 구하는 방법(finite difference)을 뜻한다.
- mjs_: 모델 편집 함수. 예: mjs_addGeom
- mjcb_: 전역 콜백 함수 포인터. 콜백은 "이 시점에 내 함수를 불러 달라"고 끼워 넣는 장치다. 예: mjcb_control은 제어 단계에서 불리는 사용자 제어 함수 자리다.
(2) 타입 앞머리
- mj: 핵심 구조체. 예: mjModel, mjData, mjOption(물리 옵션), mjContact(접촉 하나의 정보)
- mjt: 기본 타입과 열거형. 예: mjtNum(MuJoCo가 쓰는 실수 타입), mjtGeom(모양 종류), mjtJoint(관절 종류), mjtIntegrator(적분 방식)
- mjf: 콜백 함수 타입
- mjs: 모델 편집용 구조체
- mjv: 시각화 구조체. 예: mjvScene
- mjr, mjrf: 렌더링 구조체
- mjui: UI 구조체
(3) 열거형 값의 이름
- "mj + 종류 줄임말 + _ + 대문자 이름" 꼴이다. 예: mjGEOM_BOX(상자 모양), mjINT_EULER(Euler 적분), mjSTAGE_POS(위치 단계), mjDSBL_GRAVITY(중력 끄기 플래그)
(4) 파이썬에서는
- 구조체는 첫 글자를 대문자로 바꾼다: mjModel → mujoco.MjModel, mjData → mujoco.MjData
- 함수는 같은 이름 그대로다: mujoco.mj_step(model, data)
- 열거형은 mujoco.mjtGeom.mjGEOM_BOX처럼 쓴다.
- 숫자로 보면, 파이썬 mujoco 3.15.0에서 이름이 mj_로 시작하는 함수는 131개, mju_는 110개, mjv_는 29개, mjr_는 25개, mjd_는 4개다. 핵심 시뮬레이션(mj_)과 수학 도구(mju_)가 대부분이다.

6. 이름 규칙 2: mjModel과 mjData 안의 변수 이름 (헤더 파일의 주석 기준)
- n으로 시작하면 개수다.
  - nq: 관절 좌표의 개수 = qpos의 길이
  - nv: 자유도의 개수 = qvel의 길이
  - nu: 제어 입력의 개수 = ctrl의 길이
  - nbody, njnt, ngeom, nsite, nsensor: body(부품), 관절, 모양, site(센서 등을 붙이려고 위치를 표시해 둔 점), 센서의 개수
  - ncon: 지금 감지된 접촉의 개수, nefc: 지금 걸린 제약의 개수
  - nq와 nv는 서로 다를 수 있다. 왜 그런지는 3단계(기구학)에서 다룬다.
- q로 시작하면 관절 좌표 공간의 값이다.
  - qpos(위치), qvel(속도), qacc(가속도)
  - qfrc_로 시작하면 관절 좌표 공간의 힘이다: qfrc_bias(바이어스 힘), qfrc_passive(수동 힘), qfrc_actuator(모터 힘), qfrc_constraint(제약 힘), qfrc_applied(사용자가 직접 가하는 힘)
- x로 시작하거나 이름에 _x가 들어 있으면 세계 기준(Cartesian, 공간의 x·y·z 좌표) 위치와 방향이다.
  - xpos: body 기준점의 위치, xquat와 xmat: body의 방향(같은 방향을 쿼터니언 값 4개와 3×3 행렬 값 9개로 두 가지로 적은 것), xipos: body의 무게중심 위치
  - geom_xpos, site_xpos: 모양과 site의 세계 기준 위치
  - xfrc_applied: 세계 기준으로 body에 직접 가하는 힘과 비틀림
- "부품종류_속성" 꼴은 mjModel에서 부품별 값을 모은 배열이다.
  - body_mass(body의 질량), jnt_type(관절 종류), geom_type(모양 종류), geom_size(모양 크기), actuator_gainprm(모터의 게인 설정값)
  - body 배열의 0번은 세계(world) 자체다. 그래서 body를 하나만 추가해 컴파일해도 nbody는 2가 된다.
- 이름이 id나 adr로 끝나면 다른 배열을 가리키는 번호다.
  - body_parentid: 부모 body의 번호. 이것을 따라가면 나무 구조가 나온다.
  - geom_bodyid: 이 모양이 붙어 있는 body의 번호
  - jnt_qposadr: qpos에서 이 관절의 값이 시작하는 자리, jnt_dofadr: qvel에서 시작하는 자리
  - 설계 철학에서 본 "서로 찾아갈 수 있게 엮인(cross-indexed)" 구조가 바로 이런 번호들이다.
- efc_로 시작하면 제약 관련 값이다. 예: efc_force(제약 공간에서 본 제약 힘)
- 배열 모양: 헤더 주석에 (nq x 1), (nbody x 3)처럼 적혀 있다. 예를 들어 xpos는 (nbody x 3)이므로 body마다 x, y, z 세 값이 있다.
- mjData의 변수들은 "무엇에 따라 바뀌는지"로 묶여 있고, 헤더 파일에도 그렇게 적혀 있다.
  - 위치에 따라: xpos, xquat, geom_xpos 등
  - 위치와 속도에 따라: qfrc_bias, qfrc_passive
  - 위치, 속도, 제어·가속도에 따라: qfrc_actuator, qacc_smooth(제약이 없을 때의 가속도), qfrc_constraint
  - 이 묶음은 4번에서 본 mj_forward의 단계 순서와 같다.

7. "넣는 것과 나오는 것"을 실제 이름으로
- 설계도 → mjModel. 시간 간격, 중력, 적분 방식은 mjModel.opt 안의 timestep, gravity, integrator에 있다.
- 지금 상태 → mjData의 qpos, qvel, 그리고 time(시뮬레이션 시간). 모터 안에 따로 상태가 있으면 act도 상태에 들어간다.
- 모터 명령 → mjData.ctrl. 힘을 직접 가하고 싶으면 qfrc_applied나 xfrc_applied에 넣는다.
- 나오는 것 → mj_forward를 부르면 qacc, xpos, contact, sensordata 같은 계산 결과가 채워진다. mj_step을 부르면 qpos, qvel, time이 한 칸 앞의 값이 된다.

8. 지도를 이렇게 쓴다: 이상할 때 어디부터 볼까
- 모델 파일을 못 읽거나 오류가 난다 → 읽기와 컴파일 단계(MJCF·URDF → mjSpec → mjModel)
- 부품이 엉뚱한 자리에 있다 → 위치 단계의 기구학(mj_kinematics, xpos)
- 물체끼리 통과하거나 접촉이 이상하다 → 위치 단계의 충돌 검사(mj_collision, ncon, contact)와 제약 단계
- 시뮬레이션이 갑자기 처음 상태로 돌아간다 → 검사 함수(mj_checkPos 등)가 망가진 값을 보고 초기화했을 수 있다
- 물리 값은 맞는데 화면만 이상하다 → 그리기 쪽(mjv_, mjr_)
- 함수 이름만 보고도 어느 층인지 안다: mj_면 물리, mju_면 순수 계산 도구, mjv_·mjr_면 그리기, mjs_면 모델 편집, mjd_면 미분이다.

9. 핵심 세 줄
- MuJoCo는 모델 파일 → mjSpec → mjModel → mjData → mj_step(= mj_forward + 적분) → mjv_·mjr_(그리기)로 이어진다.
- mj_forward 안은 위치 → 속도 → 구동 → 가속도 → 제약 순서다. 뒤 단계만 앞 단계에 기대므로 바뀐 부분부터 다시 계산할 수 있다.
- 이름 앞머리(mj_, mju_, mjv_, mjr_, mjs_, mjd_)와 변수 앞머리(n, q, x, 부품종류_)만 알아도 코드가 전체에서 어디쯤인지 읽힌다.
```

## 0-6. 다른 도구와 무엇이 다른가 (2026-10-14)

### 핵심

- 물리 엔진(MuJoCo, Bullet, PhysX, DART)과 시뮬레이션 플랫폼(Isaac Sim, Gazebo)은 비교의 기준이 다르다. 공식 문서는 MuJoCo를 범용 물리 엔진이라고 소개한다.
- 도구별 특징:
  - Isaac Sim: Omniverse 위의 플랫폼. GPU 물리, RTX 렌더링·센서, URDF·MJCF·CAD 가져오기, Apache 2.0. Isaac Lab은 그 위의 로봇 학습 프레임워크다.
  - PhysX의 articulation도 관절 좌표 방식이다(관절 오차 0, 고리는 따로 닫음).
  - Bullet·PyBullet: 게임·시각 효과·로봇·머신러닝을 아우르는 범용 엔진(zlib).
  - Drake: TRI 지원. 모델 기반 설계와 검증, 최적화 기반 분석, hydroelastic 접촉(압력이 퍼진 접촉면).
  - Gazebo: 오픈 소스 로봇 시뮬레이터. 여러 물리 엔진, 노이즈를 넣을 수 있는 센서, SDF 형식, ROS 2와 버전 짝.
  - Newton: Warp 기반 GPU 엔진. MuJoCo Warp를 주요 백엔드로 품고 있고, Linux Foundation 프로젝트다.
  - Pinocchio: 동역학 알고리즘과 해석적 미분 라이브러리. 충돌 검사는 Coal을 쓴다.
- MuJoCo가 약하거나 하지 않는 것: 살짝 파고듦(solref·solimp·margin에 따라 달라짐)과 미끄러짐(noslip으로 줄임), 충돌용으로 메쉬를 볼록하게 바꿈(오목한 모양은 볼록 분해나 SDF로 처리), 유체 시뮬레이션은 범위 밖(간단한 유체 힘 모델 두 가지만 있음), 고리 기구는 조건으로 닫음, 사실적 렌더링·ROS 같은 플랫폼 기능.
- 고를 때 던질 질문: 시간을 돌려야 하나(아니면 계산 라이브러리로 충분한가), 영상이 사실적이어야 하나, ROS로 전체를 시험하나, 접촉면 정밀도나 최적화 도구가 필요한가, 관절 로봇 제어·강화학습을 빠르게 많이 돌려야 하나.

- 시뮬레이터마다 우선순위가 다르다. MuJoCo는 관절로 이어진 몸과 접촉과 제어를 빠르고 정확하게 계산하는 물리 엔진에 집중했다. 사실적인 카메라 영상, ROS 중심의 로봇 시스템 통합, 접촉면의 압력 분포 같은 정밀한 접촉, 유체 계산은 다른 도구가 강점으로 내세우거나 MuJoCo가 일부러 하지 않는 영역이다.

1. 지금까지 배운 것과 이번 주제의 위치
- 설계 철학: MuJoCo는 제어 연구를 위해 세 가지를 골랐다. 관절 좌표로 계산하기, 접촉을 부드럽고 볼록한 문제로 풀기, 미리 컴파일하고 메모리를 미리 잡고 설계도(mjModel)와 상태(mjData)를 나누기. 대가로 고리 모양 기구는 조건을 따로 걸어야 하고, 물체가 아주 살짝 파고들고, 설계도는 실행 중에 바뀌지 않는다고 전제한다.
- 전체 구조: 엔진 본체는 C 라이브러리이고, 주변에 파이썬 바인딩, 뷰어, GPU 구현(MJX, MuJoCo Warp)이 있다.

- 시뮬레이션 플랫폼: 물리 엔진에 3D 환경 편집, 사실적인 렌더링, 여러 가지 센서, 로봇 소프트웨어(ROS) 연결 같은 기능을 묶은 큰 프로그램이다. 예: Isaac Sim, Gazebo.

- 비유: 물리 엔진은 자동차의 엔진이고, 플랫폼은 엔진에 차체, 계기판, 내비게이션까지 갖춘 완성차다.

3. 무엇을 기준으로 비교하나
- 좌표 방식: 관절 각도로 자세를 적는가(관절 좌표), 부품마다 위치와 방향을 따로 적고 관절을 조건으로 붙잡는가.
- 접촉 모델: 접촉을 점으로 볼지 면으로 볼지, 딱딱하게 볼지 부드럽게 볼지.
- 실행 장치: CPU에서 돌리나, GPU에서 수천 개를 동시에 돌리나.
- 렌더링과 센서: 카메라 영상이 얼마나 사실적인가, 라이다나 IMU 같은 센서를 얼마나 갖췄나.
- 생태계: ROS 같은 로봇 소프트웨어와 얼마나 쉽게 연결되나, 어떤 모델 파일 형식(MJCF, URDF, SDF, USD 등)을 쓰나.
- 라이선스: MuJoCo는 Apache 2.0 오픈 소스다. 아래 도구들도 상당수가 오픈 소스다.

4. 주요 도구들
(1) Isaac Sim과 Isaac Lab (NVIDIA)
- Isaac Sim: NVIDIA Omniverse 위에 만든 로봇 시뮬레이션 플랫폼이다. NVIDIA는 로봇 시뮬레이션, 테스트, 합성 데이터 생성(학습용 가짜 데이터를 만드는 것)을 위한 도구라고 소개한다. GPU 가속 물리 엔진을 쓰고(NVIDIA 소개 페이지에는 PhysX와 Newton이 함께 언급된다), 여러 센서를 위한 RTX 렌더링과 사실적인 영상, RTX·물리 기반 센서를 강점으로 내세운다. URDF, MJCF, CAD 파일을 가져올 수 있고, OpenUSD라는 3D 장면 형식을 쓴다. Apache 2.0 오픈 소스로 공개되어 있다.
- Isaac Lab: Isaac Sim 위에 만든 GPU 가속 로봇 학습 프레임워크다. 강화학습, 모방학습, 모션 플래닝에 쓴다.
- MuJoCo와 다른 점: 카메라 영상으로 배우는 학습이나 합성 데이터 생성처럼 "보이는 것"이 중요한 일에서 강점을 내세운다. MuJoCo는 물리 계산 자체에 집중한 엔진이다.
- 참고: PhysX에도 관절 로봇을 관절 좌표 방식(reduced coordinates)으로 계산하는 기능(articulation)이 있다. PhysX 문서는 이 방식이 설계상 관절 오차가 0이고, 질량 차이가 큰 부품끼리도 잘 다룬다고 설명한다. 나무 구조가 기본이고, 고리는 관절을 따로 추가해서 닫는다. 즉 MuJoCo가 개척한 관절 좌표 방식은 이제 다른 엔진에도 들어가 있다.
(2) Bullet과 PyBullet
- Bullet Physics SDK: 공식 소개 문구는 "VR, 게임, 시각 효과, 로봇, 머신러닝 등을 위한 실시간 충돌 검사와 물리 시뮬레이션"이다. zlib이라는 자유로운 오픈 소스 라이선스다.
- PyBullet: Bullet의 파이썬 바인딩이다. 로봇, 강화학습, VR 지원을 강화했다고 소개한다.
- MuJoCo와 다른 점: Bullet은 게임과 시각 효과까지 아우르는 범용 엔진이고, MuJoCo는 처음부터 제어 연구용으로 만들어졌다.
(3) Drake (Toyota Research Institute 지원)
- 공식 문구는 "로봇을 위한 모델 기반 설계와 검증"이다. C++와 파이썬 도구 모음이고, 로봇의 동역학을 분석하고 제어 시스템을 만드는 도구들로 이루어져 있다. 최적화 기반 설계와 분석을 특히 강조한다. 운동 방정식의 구조(어떤 값이 서로 관련 없는지, 기울기를 정확히 구하는 법, 불확실성의 크기 등)를 드러내는 것을 중요하게 여기고, 마찰, 접촉, 공기역학까지 포함한 복잡한 동역학을 시뮬레이션하는 것을 목표로 한다.
- 접촉 모델: Drake에는 hydroelastic(하이드로엘라스틱) 접촉이 있다. 명목상 딱딱한 물체가 살짝 파고드는 것을 허용하고, 그 겹친 부분에 압력이 고르지 않게 퍼진 "접촉면(patch)"으로 힘을 계산한다. 접촉을 점 몇 개로 보는 방식보다 풍부하고 현실적인 접촉을 목표로 한다.
- MuJoCo와 다른 점: MuJoCo는 접촉을 점(접촉점)들로 다루고, 많이 그리고 빨리 돌리는 데 무게를 둔다. Drake는 분석, 검증, 최적화 기반 설계와 접촉면의 압력 분포 같은 정밀함에 무게를 둔다. 둘 다 "완전히 딱딱한 접촉"을 고집하지 않는다는 점은 같다.
(4) Gazebo (Gazebo Sim)
- 오픈 소스 로봇 시뮬레이터다. 이전 버전인 Gazebo Classic부터 이어진 16년이 넘는 개발 경험을 바탕으로 한다.
- Gazebo Physics를 통해 여러 물리 엔진(예: DART, Bullet)을 바꿔 끼워 쓸 수 있고, OGRE v2 같은 렌더링 엔진으로 3D 그래픽을 그린다.
- 센서: 레이저 거리 센서, 2D·3D 카메라, 깊이 카메라, 접촉 센서, 힘·토크 센서, IMU(기울기·가속도 센서), GPS의 데이터를 만들 수 있고, 원하면 노이즈(잡음)도 섞는다.
- 모델은 SDF라는 형식으로 적는다. ROS 2와 버전 짝이 정해져 있다(예: Gazebo Harmonic은 ROS 2 Jazzy, Gazebo Fortress는 ROS 2 Humble과 짝).
- MuJoCo와 다른 점: Gazebo는 로봇 소프트웨어 전체를 ROS와 함께 붙여 시험하는 플랫폼이고, MuJoCo는 엔진이다.
(5) Newton
- NVIDIA Warp 위에 만든 오픈 소스 GPU 물리 엔진이고, 로봇 연구자와 시뮬레이션 연구자를 대상으로 한다. Disney Research, Google DeepMind, NVIDIA가 시작했고, Linux Foundation의 커뮤니티 프로젝트로 운영된다. Apache-2.0 라이선스다.
- MuJoCo Warp를 주요 계산 엔진(백엔드)으로 품고 있고, GPU 가속, OpenUSD 지원, 미분 가능성(결과가 입력에 따라 얼마나 변하는지 계산할 수 있는 성질)을 강조한다.
- MuJoCo와의 관계: 경쟁자라기보다 MuJoCo Warp를 안에 품은 관계다.
(6) Pinocchio (참고: 시뮬레이터라기보다 계산 라이브러리)
- 공식 소개는 "강체 동역학 알고리즘과 그 해석적 미분의 빠르고 유연한 구현"이다. 충돌 검사는 Coal이라는 라이브러리를 쓰고, 고리 모양 기구나 마찰 접촉을 푸는 기능도 있다.
- 시간을 돌리는 시뮬레이션보다 자세 계산, 동역학 계산, 그 미분이 필요할 때 쓰는 도구다. MuJoCo도 기구학이나 충돌 검사만 따로 부를 수 있지만, 그런 계산만 필요하다면 이런 전용 라이브러리도 선택지가 된다.

5. MuJoCo가 잘 못하는 것, 또는 일부러 하지 않는 것 (공식 문서 기준)
(1) 부드러운 접촉의 부작용
- 물체가 가만히 있어도 아주 살짝 파고든다. 공식 문서에 따르면 그 깊이는 접촉 설정값(solref, solimp)과 margin이라는 설정에 따라 달라진다.
- 부드러운 제약 모델 때문에 물체가 조금씩 밀리거나 미끄러지는 현상(drift, slip)이 생길 수 있다. 이를 줄이려고 noslip이라는 후처리 풀이기가 따로 있고, noslip_iterations 옵션으로 켠다. 엔진이 스스로 이 약점을 알고 대책을 넣어 둔 것이다.
(2) 오목한 모양의 충돌
- 메쉬(삼각형 여러 개로 만든 3D 모양)는 충돌 계산을 위해 볼록한 모양으로 바뀐다(공식 문서 표현: convexified). 볼록하게 바꾼다는 것은 고무줄로 물체를 감싼 것처럼 오목한 곳을 메운 껍질로 계산한다는 뜻이다.
- 그래서 컵처럼 오목한 모양은 안쪽이 메워진 것처럼 계산된다. 오목한 모양을 제대로 다루려면 볼록한 조각 여러 개로 나누거나(볼록 분해), SDF(부호 거리장: 공간의 각 점에서 표면까지의 거리를 담은 표현) 같은 다른 표현을 쓴다.
(3) 유체
- 공식 문서: "제대로 된 유체 역학 시뮬레이션은 MuJoCo의 범위를 벗어나며, MuJoCo가 돕고자 하는 응용에는 너무 느리다."
- 대신 간단한 유체 힘 모델이 두 가지(관성 기반, 타원체 기반) 있다. 주변의 물이나 공기 자체는 계산하지 않고, 날기나 헤엄치기 같은 핵심 효과만 힘으로 흉내 낸다.
(4) 고리 모양 기구
- 기구는 나무 구조로만 직접 표현할 수 있고, 고리는 "붙여 두는 조건"으로 닫는다. 이 조건도 부드럽게 풀리므로 이음매가 아주 살짝 어긋날 수 있다. PhysX도 나무 구조가 기본이고 고리는 따로 닫는 것을 보면, 관절 좌표 방식에 공통된 성질이다.
(5) 플랫폼 기능
- MuJoCo는 물리 엔진이다. 사실적인 카메라 영상(RTX 렌더링), 노이즈가 섞인 다양한 센서, ROS와의 연동 같은 것은 Isaac Sim이나 Gazebo 같은 플랫폼이 강점으로 내세우는 영역이다.
- MuJoCo에도 OpenGL과 Filament 렌더러, 카메라, 여러 센서가 있지만, 중심 목적은 물리 계산이다.

6. 한눈에 정리
- MuJoCo: 물리 엔진. 관절 좌표, 부드럽고 볼록한 점 접촉. CPU와 GPU(MJX, MuJoCo Warp). 강점: 관절 로봇, 접촉, 제어를 빠르고 정확하게, 접촉 중에도 역동역학. 약하거나 하지 않는 것: 살짝 파고듦과 미끄러짐, 오목한 메쉬, 유체, 플랫폼 기능.
- Isaac Sim / Isaac Lab: 플랫폼. GPU 물리, RTX 렌더링과 센서, OpenUSD. 강점: 사실적인 영상, 합성 데이터, 대규모 GPU 학습.
- Gazebo: 플랫폼. 여러 물리 엔진을 바꿔 끼움, 노이즈를 넣을 수 있는 센서, ROS 2 연동. 강점: ROS로 로봇 시스템 전체를 시험.
- Drake: 도구 모음. 최적화 기반 설계와 분석, hydroelastic 접촉. 강점: 분석과 검증, 접촉면의 압력 분포.
- Bullet / PyBullet: 범용 엔진(게임, 시각 효과, 로봇, 머신러닝).
- Newton: GPU 물리 엔진(Warp 기반). MuJoCo Warp를 주요 백엔드로 품음. 미분 가능, OpenUSD.
- Pinocchio: 동역학 계산 라이브러리(충돌은 Coal). 강점: 빠른 동역학 알고리즘과 해석적 미분.

7. 어떻게 고르나: 스스로 던질 질문
- 시간을 앞으로 돌리는 시뮬레이션이 필요한가, 아니면 자세·동역학·충돌 계산만 필요한가? 후자라면 MuJoCo의 일부 기능만 쓰는 셈이고, Pinocchio 같은 전용 라이브러리도 후보다.
- 카메라 영상이 사실적이어야 하나? 그렇다면 Isaac Sim 같은 플랫폼이 강점을 내세우는 영역이다.
- ROS로 로봇 소프트웨어 전체를 붙여 시험하나? 그렇다면 Gazebo가 그 용도로 만들어졌다.
- 접촉면의 압력 분포까지 정밀해야 하거나, 최적화·검증 도구가 필요한가? 그렇다면 Drake가 그쪽에 무게를 둔다.
- 관절 로봇의 제어나 강화학습을 빠르게, 많이 돌려야 하나? 접촉 중의 역동역학이 필요한가? 그렇다면 MuJoCo의 주 무대다.
- 위의 강점은 각 도구가 스스로 내세우는 공식 설명이다. 실제로 고를 때는 자기 문제로 작게 시험해 보고 고른다.

8. 이걸 알면 짐작할 수 있는 것
- 쥐고 있는 물체가 손에서 천천히 미끄러진다 → 부드러운 접촉 때문에 생기는 slip일 수 있다. noslip 옵션이나 접촉 설정값을 의심해 본다.
- 컵 안에 공을 넣었는데 공이 컵 위에 떠 있다 → 컵 메쉬가 볼록한 껍질로 바뀌어 안쪽이 메워졌기 때문이다. 볼록 분해 같은 처리가 필요하다.
- 물속 로봇 주변의 물 흐름을 보고 싶다 → MuJoCo의 범위 밖이다. MuJoCo의 유체 모델은 힘만 흉내 낸다.
- 다른 시뮬레이터에서 쓰던 모델을 가져왔더니 다르게 움직인다 → 엔진마다 좌표 방식, 접촉 모델, 설정값이 다르기 때문에 같은 모델도 결과가 다를 수 있다.

9. 핵심 세 줄
- MuJoCo는 관절 로봇, 접촉, 제어를 빠르고 정확하게 계산하는 데 집중한 물리 엔진이다. Isaac Sim이나 Gazebo는 렌더링, 센서, ROS까지 묶은 플랫폼이라 비교의 기준이 다르다.
- 관절 좌표 방식은 PhysX 같은 다른 엔진도 받아들였고, 접촉 모델은 도구마다 다르다(MuJoCo는 부드러운 점 접촉, Drake는 압력이 퍼진 접촉면).
- MuJoCo가 약하거나 하지 않는 것은 살짝 파고듦과 미끄러짐(noslip으로 줄임), 오목한 메쉬(볼록하게 바뀜), 유체(간단한 힘 모델만), 사실적인 렌더링이나 ROS 같은 플랫폼 기능이다.

(1) Overview(개요)
- 소개, 핵심 기능, 모델의 형태, 예시, 모델을 이루는 요소를 설명한다.
- 끝부분의 "Clarifications(헷갈리기 쉬운 점)"가 특히 중요하다. 시뮬레이션이 발산하는 경우(Divergence), 단위가 정해져 있지 않다는 점(Units are unspecified), 예상 밖의 충돌(Surprising Collisions), 부드러움과 미끄러짐(Softness and slip), 관절 좌표(Joint coordinates), 떠 있는 물체(Floating objects) 같은 주제가 들어 있다. 이상한 결과가 나왔을 때 가장 먼저 볼 곳이다.
(2) Computation(계산)
- 물리를 어떻게 계산하는지 설명하는 장이다.
- 부드러운 접촉 모델: 왜 부드러운가(현실성, 계산 효율, 연속 시간, 역동역학과 최적화)
- 일반 틀: 구동 모델, 수동 힘, 수치 적분, 상태(The State)
- 제약 모델: 붙여 두는 조건(Equality), 마찰 손실, 한계(Limit), 접촉(Contact)
- 제약 풀이기, 그리고 별도 페이지인 유체 힘
- 설계 철학에서 본 선택들의 근거가 여기에 있다.
(3) Modeling(모델링)
- MJCF로 모델을 만드는 법이다. 기구 트리, 기본값 설정, 좌표계와 방향, 풀이기 설정값(solref, solimp 등), 마찰, 접촉 설정값, 구동기, 센서, 카메라, 변형체, 파일 포함하기, URDF 확장 같은 내용이 있다.
(4) XML Reference(XML 사전)

(5) Programming(프로그래밍)
- C API로 프로그램을 짜는 법이다. 시작하기, 소스로 빌드하기, 헤더 파일, 버전 호환, 이름 규칙이 있다.
- 하위 페이지: Simulation(초기화, 시뮬레이션 루프, 상태와 제어, 순동역학과 역동역학, 멀티스레드, 데이터 배치, 자코비안, 접촉, 좌표계 변환 등), Visualization(그리기), UI, Model Editing(mjSpec), Samples(예제 프로그램), Extension(플러그인).

(6) API Reference(API 사전)

(7) Python

6. C 예제 프로그램 (저장소의 sample 폴더, 공식 문서 Samples 페이지)
- simulate: 기능을 다 갖춘 대화형 시뮬레이터(뷰어 앱)
- basic: 가장 작은 대화형 시뮬레이터. 모델 파일을 받아 실제 시간에 맞춰 시뮬레이션하며 초당 60장으로 그린다.
- compile: 내장 파서와 컴파일러로 모델 형식을 바꾼다(MJCF, URDF, MJB → MJCF, MJB, TXT). MJB는 컴파일된 모델을 그대로 저장한 이진 파일이다.
- testspeed: 모델의 시뮬레이션 속도를 잰다. 정해진 걸음 수만큼 돌리면서 접촉 수, 제약 수, CPU 시간 통계를 모은다.
- record: 시뮬레이션을 화면 없이 그려서 픽셀 값을 파일로 저장한다. ffmpeg 같은 도구로 영상으로 바꿀 수 있다.
- render: 모델의 한 장면을 화면 없이 그려서 PNG 이미지로 저장한다. 물리 기반 렌더링(PBR)을 지원하는 Filament와 기존 OpenGL 렌더러를 모두 지원한다.

8. MuJoCo Menagerie: 잘 만든 로봇 모델 모음
- Google DeepMind가 골라 관리하는 고품질 MuJoCo 모델 모음이다.
- 왜 필요한가(공식 문서): "물리 시뮬레이터는 시뮬레이션하는 모델만큼만 좋다. MuJoCo처럼 모델링 선택지가 많은 강력한 시뮬레이터에서는 예상대로 움직이지 않는 '나쁜' 모델을 만들기 쉽다." 그래서 바로 잘 동작하는 잘 설계된 모델을 모아 두었다.
- 분류: 두 발 로봇, 인간형, 모바일 매니퓰레이터(바퀴 달린 몸에 팔이 달린 로봇), 네발 로봇, 그리퍼와 손, 로봇 팔, 드론, 생체역학 모델
- 품질 등급: A+부터 C까지 있다. A+는 시스템 식별(실제 로봇을 측정해서 모델의 물리 값을 맞추는 일)을 제대로 거친 값이고, A는 현실적인 값이지만 제대로 식별하지는 않은 값이다.
- 쓰는 법: 각 모델 폴더의 scene.xml을 불러서 본다. 예: python -m mujoco.viewer --mjcf mujoco_menagerie/unitree_go2/scene.xml. 모델마다 필요한 최소 MuJoCo 버전이 그 모델의 README에 적혀 있다.
- 저장소에는 모델 폴더가 69개 있다(assets, python, test 폴더는 제외하고 센 것이다). 예: unitree_go2, unitree_g1, unitree_h1(Unitree 로봇), robotis_op3(쓰임새에서 본 축구 연구의 로봇), boston_dynamics_spot, franka_emika_panda, kuka_iiwa_14, universal_robots_ur5e, shadow_hand, wonik_allegro(Allegro 손), skydio_x2(드론)
- 공부에 쓰는 법: 모델링 단계에서 "잘 만든 MJCF는 어떻게 생겼나"를 보는 본보기로 읽기 좋다. 뷰어로 열어 움직여 보는 것만으로도 감을 잡는 데 도움이 된다.
